# ALL IN 365 V2 — Train, Routes/Routines and Event Plan: Founder-Approved UX Baseline

**Decision authority:** Founder discussion on 2026-11-12. **Status:** approved product design requirements, NOT assertion of implemented/validated screens, and NOT approval for production migration/grants/deploy/publication. **Primary issue:** ALL-246. Related owners: ALL-250 Today, ALL-249 Progress, ALL-243 Completed Activity, ALL-234 Coach Race Strategy, ALL-239 all-sport goals, ALL-244 EventHub, ALL-245 Watch, ALL-254 UI/UX.

## Authority and conflict resolution
- This document consolidates the latest explicit founder decisions and **supersedes earlier contradictory V2 navigation and calendar descriptions**, including “Calendar / Plans / Progress,” “Calendar / Plans” only, “Routes” without Routines, “Month / Week / Day,” a vertical week list, large Train navigation tiles, or a saved-routes-only workspace.
- Keep approved V1 behavior as the baseline where explicitly selected. Do not mistake a design prototype or source-level fixture for a tested installed app. New founder changes should update this document and linked issue rather than silently resurrecting old directions.
- Global main tabs remain Today / Fuel / Train / Community / Coach. Progress is a compact clickable section on **Today**, linking to the standalone customizable all-sport Progress destination; body-progress photos/private measurements belong under Profile, not Train.

## 1. Train navigation and spatial hierarchy
- Train has **three compact top-level horizontal segmented tabs: Calendar / Plans / Routes/Routines**. Do not use big cards, oversized tab headers/icons or tall navigation. Preserve reasonable accessibility target sizes on narrow phones.
- Calendar is the default. While Calendar is selected, a distinct second compact segmented row offers **Month / Week only**.
- Plans contains **Training Plan / Event Plan**. Both should be compact section choices; daily scheduling lives in Calendar, not duplicated in Plans.
- Routes/Routines contains **Routes** (full interactive mapping/builder) and **Routines** (reusable workout structures). Do not relocate Routes to nested Plans or remove the Routines half of the name.
- The content of the active page owns the available screen real estate.

## 2. Calendar
- **Month:** retain the founder-approved month grid with meaningful workout/rest/day markers. Selecting a date opens its containing Week with that selected date active.
- **Week:** exactly **seven horizontal selectable day blocks**, all visible in one row, never a vertical 7-row list. When the athlete taps one, **that day's workout cards appear directly below the same horizontal calendar**, without navigation to a separate day screen/tab. No Daily tab/view.
- Below selected-day workouts, show **+ Add Workout**. Represent planned, active, completed, missed, rest, recovery, unavailable and event states from canonical evidence, not placeholders presented as real workouts.
- **Card tap contract:** (a) A **today planned, unfinished** workout opens sport-specific **Start Training / pre-workout launch**. If already active, **Resume** the same canonical session; no duplicate. (b) Any **completed** workout, including one completed today, opens its **exact Completed Activity** by canonical completion identity (Overview / Details / Coach). (c) A **future planned** workout opens a **small synopsis/preview** of sourced expected purpose, structure, duration/targets and a **short personalized Coach explanation** of why this is scheduled; offer **Change**. (d) Change requests a Coach-supported proposal and explicit review/accept before any guarded Training revision—never silently mutate the plan. (e) A **past missed/uncompleted** planned workout must never be routed to fictitious Completed Activity; show true status and appropriate review/reschedule pathway.
- Day/date comparisons use athlete-local dates and truthful complete owner-scoped read models; no automatic moving of missed workouts.

## 3. Training Plan
- Compact management view for active training plan, current goal/phase, plan duration/progression, multi-sport weekly structure, Coach explanation/review, plan creation and previous plans.
- This is the **management/approval** area; the actual workout schedule remains in Calendar.
- Display sport-adaptive summaries—not fixed running-miles/long-run metrics for cyclists, swimmers, lifters or multi-sport athletes. Coach is proposer, Training owns accepted revisions, preserve historical plan revisions and completed evidence.

## 4. Routes/Routines — founder explicitly chose V1 builder
- **Port and adapt V1's existing full map-based Route Builder, never replace with a reduced saved-route list or duplicate builder architecture.**
- V1 reference repository: `allinproject/ALL-IN`, branch `integration/native-watch-v301`. Main modules include `Native/src/app/training/routes.tsx`, `route-editor.tsx`, `coach-routes.tsx`, `Native/src/components/RouteMapCanvas.tsx`, `Native/src/lib/trainingRouteEditor.ts`, `trainingRouteGeneration.ts`, `trainingRouteProviderClient.ts`, `Native/src/data/trainingRouteClient.ts`, `trainingRouteDraftStorage.ts`, `supabase/functions/training-route-provider/index.ts`.
- Preserve interactive map, set/drag start/end/waypoints, freehand tracing, route editing, undo/redo, loop/out-and-back/point-to-point, provider-backed rerouting, evidence-backed route geometry/distance/elevation/surfaces/access/terrain, saved/rename/favorite/duplicate/delete/reopen, draft recovery, Coach route generation with edit/approval, and confirmed attachment to Training workouts.
- **Coach proposed route opens this SAME full-screen interactive map editor with Coach's candidate route already drawn as an editable overlay** (not a text-only suggestion, detached preview or alternate map screen). Immediately display proposed geometry, available evidence-backed distance/elevation/terrain and an explicit 'Coach proposal' / not-yet-saved distinction. Athlete can zoom/pan, inspect, move/reorder/add/remove waypoints, freehand edit, change route type, undo/redo and request provider-backed recalculation; material changes invalidate stale measurements. Keep a short Coach explanation of how the route fits the workout and conditions. **Only explicit athlete acceptance/Save** persists the route or attaches it to a planned workout. Reject/Back leaves accepted routes and Training plans unchanged. If provider evidence/geometry is unavailable, show that limitation and never draw an invented verified route. Resume/draft behavior remains account-scoped. Both Build a Route and Ask Coach share the same editor, state model and save pathway.
- GPX import/export and Watch/offline turn guidance require explicit actual source/device verification; do not falsely claim them already working. Reuse existing V2 canonical owner/security and approved plan/session references, not unreviewed V1 database/RPC migrations. Map tiles and provider operations need licensing, network, security, device and reliability checks.
- Routines: reusable workout routines in the paired workspace. Exact routine screen requires separate detailed founder review; preserve existing V1 behavior rather than inventing.

## 5. Event Plan — all-sport, not only racing
- Under Train → Plans → **Event Plan**, present event-level records for running/ultra, cycling, triathlon, swimming, strength/powerlifting, hybrid competitions, etc. Race-specific UI is conditional; noncompetitive athletes are not forced to create events. Multiple upcoming events supported as an existing product requirement, though exact selection interface may be refined.
- **Approved preferred event detail direction (founder explicitly liked design):** compact sections **Course / Strategy / Race Day**. These were shown as an interactive concept; do not treat every proposed micro-interaction as a separately locked decision.
- **Course:** official course map/GPX, sourced geometry, distance, elevation profile and per-section climbs/descents, terrain/surface, named aid stations/checkpoints, cutoffs, organizer rules, provenance/version and missing/conflicting data. Race-specific aid and elevation data must never be invented. Athlete-supplied GPX does not prove organizer-verified aid stations.
- **Strategy:** individualized Coach explanation of pacing/effort (including hills and walk/hike strategy when applicable), fueling/hydration/electrolytes based on real duration/tolerance/conditions/aid supply, appropriate gear and weather/rules. No unsupported numbers/device data. Review major changes.
- **Race Day:** timing/checkpoint and cutoff view, planned stops, crew/drop bags, aid restock checklist and contingencies, validated phone/Watch navigation when actually supported.
- If official course updates, invalidate/review affected strategy packages. Preserve one canonical event ID/version linking Event Plan, event registration/participation, Coach, EventHub, Calendar and eventual completion.

## 6. Create Event Plan — website URL is prominent and also feeds EventHub
- Event creation starts with a **clearly visible official Event website URL input and Get Event Information action**. The athlete may also provide official GPX/files or manual details. Do not bury URL in an advanced upload flow.
- Secure server-side source intake gathers organizer-backed name, event type, date/time/timezone, venue, distance/discipline, official course/map/GPX, aid stations/checkpoints/cutoffs and rules **only where published**. Show exact sourced/unknown/conflicting info for athlete review and allow provisional private plans when data unavailable.
- URL intake must identify the **correct event edition** and check for an **existing canonical EventHub event/group**. If one exists, offer **Open/Join EventHub**; otherwise prepare creation of the corresponding EventHub group through the approved owner and permissions. No duplicate groups for same edition; handle URLs with tracking parameters and concurrent creation.
- **One event identity, two experiences:** athlete-private Event Plan with preparation/strategy; EventHub is the event-specific community workout-sharing group joined through the supplied event URL. EventHub is NOT a generalized event discovery/search/marketplace. No automatic public post, joining or disclosure; explicit participation/sharing choice. Creating a private event plan must not expose private plans, locations or health information.
- Secure URL handling (https, SSRF/redirect restrictions, source provenance, size/rate limits), owner/RLS controls, canonical event record and idempotency required before enabling actual publishing/joins. Existing ALL-244 owns EventHub; ALL-234 owns source-grounded race strategy; ALL-246 owns Train UI.
- Creation walkthrough currently envisioned: Event identity & URL → course/official evidence → user goals → explicit Coach plan/strategy review → approved Event Plan; event group linkage presented alongside the review. A URL lookup or strategy preview is not itself publication/approval of changes to Training.

## 7. Routines — completed workout conversion and Coach adaptive learning (founder-approved 2026-11-12)
- In Train → Routes/Routines → Routines, athletes can **Save as Routine** from a Completed Activity, retaining useful repeatable workout structure: sport, ordered strength exercises and prescribed sets/reps/rest, interval blocks and intensity targets, swimming sets, equipment, warm-up/cooldown and sport-specific units as supported by the actual source data. Show an editable review of the proposed reusable template before saving; do not mistake actual performance measurements for future prescriptions or manufacture missing targets.
- Saved routines are **reusable templates**, not completion records and not automatically scheduled workouts. A completed source activity remains an immutable, attributable historical record; later edits/duplicates/deletions of its routine do not rewrite the original completion. Routine ownership is private/account-scoped by default and must participate in export/deletion lifecycle.
- **Coach must use the athlete's saved routines as relevant authorized context for Training Plan synthesis and adaptations**, alongside actual completed workout outcomes, equipment/availability, goals, recovery and athlete feedback. Learn from explicit saves, edits, favorites, uses and athlete responses, but distinguish *preference evidence* from *performance and ability evidence*: saving/favoriting alone never proves exercise completion, adherence, readiness or safe load capacity.
- Coach should recognize preferred exercises, interval structures, sports, realistic durations, available equipment, frequently chosen routines and observed performance/tolerance; it can propose reuse or carefully adapted variants that fit current goals, periodization, recovery and injury/safety constraints instead of blindly repeating favorites. Support cross-sport and beginner athletes. Explain in plain language when a saved routine influenced a proposal, allow athlete corrections/overrides, and do not infer a permanent preference solely from one save.
- Coach **proposes** including/changing a routine in a training plan or calendar; accepted Training is the only authority to apply changes after explicit athlete review. User can edit/delete saved routines without erasing completed evidence. No automatic public sharing or cross-account routine leakage.
- Reuse existing V2 canonical Completed Activity → Training/Coach read contracts and routine/template ownership; do not create competing workout storage or a separate Coach learning database solely for this feature. Verify source-backed conversion, athlete isolation, editing/history integrity, plan revision acceptance and lifecycle tests before calling implemented.
- **Founder-approved upgraded Create/Edit Routine direction after competitor review (2026-11-12):** Use a **Hevy-inspired detailed strength routine editor** (ordered exercises, multiple set types including warm-ups where meaningful, weight/rep/effort targets, rest timers, notes, custom exercises, supersets/circuits, rearranging and reusable templates) while keeping **Strong-inspired compact rapid input** and clear update-original vs preserve-original decisions. For **endurance sports**, adapt the *same routine workflow* to **TrainingPeaks-inspired structured interval blocks** (warm-up, work/recovery, cooldown, repeat groups, intensity using sport-supported pace/HR/power/RPE, distance/time and swim sets) and **TrainerRoad-inspired editable/reusable interval snippets**. These are functional references, not copying proprietary interfaces or exact layouts.
- **Coach adaptation inspired by Fitbod** uses authorized workout outcomes, saved routines, routine edit/use patterns, goals, equipment and recovery to make explainable personalized proposals; athlete can review/edit Coach-proposed routine in the SAME builder. Preserve the original routine, historical workouts and exact saved-version references whenever variations/progression are proposed; never automatically overwrite the template based on a single session.
- Saved routines should support starting through canonical sport-specific Start Training, scheduling through Calendar, and saving an actual Completed Activity as a new routine. Explore reliable cached/offline access to saved templates subject to security/device validation.
- **FOUNDER-APPROVED ROUTINE START INTERACTION — 2026-11-12:** When a saved routine is opened, display its original contents with **Start Workout** immediately available as the default, with no mandatory `Repeat Exactly / Adapt with Coach` choice. When Coach has a useful evidence-grounded suggestion, show a **small optional inline Coach suggestion** explaining the exact proposed change (such as targets, sets, reps, interval duration or effort). Athlete can choose **Keep Original** or **Apply Change**; no suggestion card when no relevant evidence-based adjustment exists. Applying a suggestion affects **this workout/session preview only**; it must not overwrite the saved routine or accepted training plan. Athlete may **Edit This Workout** before launch. Starting routes through the canonical sport-specific Start Training and active session lifecycle (resume existing active session, never duplicate). After completing a modified workout, optionally prompt to **Update Saved Routine** or **Keep Original**, with explicit consent, version/history integrity and Completed Activity unchanged. Coach must use authorized real athlete context, explain why, and must never impose changes, infer performance from favorites alone or claim a fabricated personalized prescription. This inline-default pattern supersedes the previously open start-choice UX question.


## 8. Start Training — run/bike route attachment (founder-approved 2026-11-12)
- For **outdoor running and outdoor cycling Start Training** show one **compact optional Route section** before the Start button. Include state `No route selected` or the selected route's name and source-backed thumbnail, distance/elevation/terrain where available; do not crowd the launch screen.
- Provide **Choose Saved Route**, **Build a Route**, and **Ask Coach for a Route** actions. All three must reuse the approved V1-based **same full-screen interactive route map/editor**. Selecting a saved route previews and confirms its version; Build starts blank; Ask Coach starts with Coach's evidence-backed proposed line already drawn and editable. Returning from editor brings the selected/proposed route back into Start Training with explicit **Use This Route** confirmation and ability to **Change/Remove** before launch.
- Existing workout/plan route attachments, session route choice and Coach proposals must preserve their canonical route identity and version; selecting a route for **this session** must not silently rewrite an accepted plan or saved route. Check reasonable distance/sport/route access mismatches and explain them, not silently force matching. User can start without a route. Indoor workouts should not demand outdoor navigation; sport-specific support can expand later without forcing all sports into this setup.
- Start Training's other compact setup remains workout synopsis, relevant equipment/bike/shoe, Coach notes and optional live HR/pacing/fueling/navigation alert preferences. Route guidance appears only where a route is selected and phone/Watch navigation is actually supported/validated. Route loss/staleness/offline unavailability must be shown, never present unverified turn-by-turn as reliable.
- Design approval only; actual mounted UI, canonical backend attachment, route map, phone/Watch navigation and on-device tests still require separate acceptance.

## 9. Phone-configured, Watch-executed standalone training (founder-approved 2026-11-12)
- **Primary UX:** athletes may configure all workout options on the phone, then leave the phone behind. On Watch, the already-configured workout should be visible with a prominent **Start [Sport]** button; resume the same session if active. Watch setup is not required to repeat the entire phone editor.
- Phone configuration includes canonical planned/saved workout or routine and steps, selected shoes/bike where relevant, route and exact route/course/version, elevation-aware target splits/time goal and approved strategy where supported, HR zone/alerts, pace/effort cues, fuel/hydration reminders, navigation prompts, workout mode and other authorized sport-specific settings.
- **Preflight synchronization** must package the immutable/versioned accepted workout/route/strategy snapshot and alert policy for the Watch with an exact athlete/account and session identity. Acknowledge receipt, compatibility, integrity and locally available **offline** route/section/splits before marking **Ready on Watch** on phone or Watch; never confuse 'sync queued' with 'offline ready'. Clearly show missing/unavailable capabilities and offer retry; check latest version before starting when connected. Watch can still start basic recording without unavailable optional route or smart guidance, with honest degraded status and athlete control.
- The Watch locally handles GPS/heart-rate capture, elapsed time, pause/resume/finish, downloaded route position/section, live per-mile targets/elapsed comparisons, HR zone prompts, timers and meaningful haptics using bounded local algorithms rather than continuous AI/network calls. Audio/navigation availability must reflect actual supported Watch capabilities and preloaded data. No requirement to carry iPhone, retain Bluetooth connection or cellular service to **execute an already-prepared workout**.
- Watch should offer essential override actions (start/resume, pause/finish, simple mode or alert toggles and Other Activity for spontaneous workouts) without forcing full phone-sized complex configuration. Preserve accessible screen readability and battery-conscious prompt frequency.
- Sync completed activity and buffered sample events after reconnection to the SAME canonical owner-scoped session/activity; do not create duplicate sessions, lose offline data, or overwrite newer plan/route versions. Protect account switching, retries, interrupted transfer, stale pending packages, workout restart and insufficient Watch storage/battery.
- This is a design contract. No claim of current native WatchOS target/device validation. Physical Watch/iPhone tests must confirm offline start, phone absent, route/elevation and pacing guides, HR haptics, reconnection, duration/battery reliability before launch.

## 10. Training Setup supports phone OR Watch start, and optional Live Props (founder clarification 2026-11-12)
- **ONE shared workout setup screen, two explicit outcomes:** `Save & Sync to Watch` prepares the configured workout for later Watch start without starting recording; `Start on This Phone` starts the same workout's real canonical active session immediately on the phone, with recording/timer and sport-specific Active Training. Both are clearly labeled and coexist, rather than forcing everyone into Watch-only training. An athlete need not have a Watch. Prefer layout that preserves quick access to each action and clearly distinguishes saving from starting; no implicit start on Save.
- The setup includes relevant sport-specific route, reviewed elevation-adjusted pacing plan, shoe/bike, HR zone/alerts, Coach cues, fueling/hydration, navigation and appropriate mode. A phone starter uses the same approved configured snapshot. Watch starters get reliable acknowledged, versioned offline package transfer first and explicit `Start [Sport]` on the Watch; no phone required after transfer. On either device, `Resume` must target the same already active/paused workout, never duplicate canonical sessions. Multi-device attempts must be coordinated via existing Training session authority.
- **Live Props is a separate optional setting** from functional Coach pace/HR/navigation prompts: allow athletes to opt in to motivational encouragement/props received during training, potentially from authorized friends/community if the existing Community permissions and product flow support it. It must be clearly user-controlled with mute/off and unobtrusive delivery; default-private and avoid exposing workout location, live route, timing, personal metrics or a person's active workout to an audience merely because Props is enabled. Any ability for another user to send props needs its own privacy, viewer-authorization, rate/abuse and notification review and explicit sharing consent. Do not promise real-time network props while the phone/Watch is offline; queued props can be delivered later only if supported and appropriate. If by 'Live Props' the founder means something else, clarify with founder before extending the community workflow.
- **Independent controls:** HR alerts, Coach guidance, navigation and Live Props must be separately configurable; Coach guidance should continue offline when supported by downloaded strategy and local sensor data, while live social encouragement requires connectivity and permissions. Prevent duplicate cues if phone and Watch are connected; respect audio/haptic delivery accessibility and battery limits.
- Personal changes to this workout do not silently change accepted Training plan, saved routine/route, other workouts or athlete defaults. `Save as Default` is an explicit separate user action. Saving setup is not Completed Activity and must not record GPS/HR until actual Start.
- This supersedes prior Watch-exclusive interpretation of phone setup while preserving the founder-approved **phone-configure / sync / Watch-start** experience for athletes who leave their phone home. Phone-only active recording is now explicitly required; neither implementation nor real-device validation is claimed.
