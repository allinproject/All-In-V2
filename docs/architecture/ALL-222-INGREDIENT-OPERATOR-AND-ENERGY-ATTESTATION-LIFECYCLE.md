# ALL-222 / ALL-251 — Ingredient reviewer operator and credential lifecycle

**Status: implementation contract and native isolated acceptance only. Not an operational enrollment, production credential, or authorized deployment.** Version: 2026-11-12.

## Canonical ownership and trust boundary

The ALL-222 Ingredient Database remains the sole authority for shared foods, aliases, profile facts, status and audit. Reviewer identities are **not athlete accounts** and never use a mobile JWT, a user-editable claim, a service-role API key, a boolean passed by a client, or a generic provider cache. Every successful mutation requires an actual PostgreSQL `session_user` corresponding to an individually authenticated operator DB login, membership in the NOLOGIN `allin_v2_ingredient_reviewer` group, and an enabled, verified, **unexpired** private registry binding. No published operator or credential currently exists.

Operator identity proof is an external **IdP-verified immutable issuer+subject**, with an auditable administrative approval and MFA. The staging database records that proof's issuer, subject, verified timestamp and credential **vault reference**, never passwords, tokens, MFA recovery codes or private keys. The database **cannot independently verify the external identity proof**; enrollment MUST be performed by a separately authorized security administrator after verifying it out-of-band. Storing an arbitrary issuer/subject value or signing in with an athlete's Supabase Auth account is not verification.

The proposed SQL owners:
- `docs/architecture/sql/V2-INGREDIENT-OPERATOR-CREDENTIAL-LIFECYCLE-CANDIDATE.sql` — private verified binding, credential expiry and immutable enrollment/change/revocation audit
- `docs/architecture/sql/V2-INGREDIENT-CANONICAL-REVIEW-WRITER-CANDIDATE.sql` — controlled writer enforcing enrollment, membership, profile revision, source hash, idempotency and atomic audit
- `docs/architecture/sql/V2-INGREDIENT-USDA-ENERGY-ATTESTATION-CANDIDATE.sql` — source-digest and version-bound energy attestation, same reviewer gate; publication remains prohibited

## Authorized operator provisioning sequence (future release, not yet executed)

1. Designate a named human operator and a second approver in ALL-251/ALL-222. Independently verify the IdP issuer/subject, MFA posture, role justification, training and incident contact. Capture proof reference, authorization decision, credential TTL, and a separation-of-duties review. Do not infer this from the user's account email.
2. Authorize a **dedicated per-person PostgreSQL LOGIN** with least privileges, a random credential generated and rotated inside an approved secret manager and accessible only by the trusted back-office executor. Store *only* the secret-manager reference in the private registry; never commit SQL with a password, output a connection string to logs, store the secret in GitHub or in the mobile bundle, or expose this role through PostgREST.
3. Use a trusted **direct PostgreSQL connection or approved session pool**, not a shared transaction pool with ambiguous identity; verify TLS, server certificate and `session_user` at the database boundary. The Data API and mobile SDK do **not** receive this credential. Role membership alone does not authorize review.
4. An owner/admin with approved change control records verified `identity_issuer`, `identity_subject`, `identity_verified_at`, `credential_vault_reference`, `credential_expires_at`, `enrollment_reference`, then enables the private registry and grants membership to the NOLOGIN reviewer role. The binding enforces one issuer+subject, one vault reference, immutable operator principal and time-based expiry checked on each call. Reject pooled or generic login reuse.
5. Exercise authorization-denial tests from an ordinary authenticated athlete, anon, service_role, unregistered operator, disabled operator, expired login and a forged GUC. Confirm positive controlled review operations have private review and credential audit receipts. Never grant direct shared-table or private audit-table writes to reviewer logins.

## Rotate, suspend, revoke and recover

- **Rotate:** confirm the same immutable human identity, create a new secret version in the vault, update the private vault reference/expiry via approved owner action, rotate the actual PostgreSQL login secret and terminate all old backend sessions. Recheck credentials and record old/new expiry, change ticket and approver; do not reuse a previous secret or issue a new shared login.
- **Suspend/revoke:** set `enabled=false` and `revoked_at` through approved owner action *first*, then revoke reviewer role membership, disable database login, rotate/remove the secret and terminate existing sessions. The next review function call must deny. A transaction already admitted before revocation may complete; revocation needs transaction/connection drain and in-flight operation reconciliation, not just an eventual JWT change.
- **Identity change:** issuer or subject changes require disabling the old binding and provisioning a new dedicated login. The trigger rejects changing the identity in place and disallows erasing the registry row.
- **Recovery:** require fresh IdP/MFA verification, independent approval, new credentials, review of audit history and explicit re-enrollment. Do not auto-reenable from stale sessions, archived emails or copied app claims.
- **Retention:** private credential and energy attestation events are append-only; exact retention periods, export access and legal handling remain ALL-251/privacy-owner decisions. An eventual bounded retention worker would need separately reviewed archival receipts; do not bypass the immutable trigger to purge ad hoc.

## USDA energy method and provenance

A reviewed USDA Foundation source must carry a pinned official bulk archive digest, a **canonical per-food JSON SHA-256**, immutable source-energy evidence for each reported FDC method and a 100 g/kcal basis. The selected version is `usda-fdc-energy-specific-legacy-v1`: prefer FDC nutrient ID **2048** (Atwater specific) if present; otherwise **1008** legacy energy. ID **2047** (Atwater general) can be retained as evidence but **cannot be silently selected**. The immutable attestation binds the selected method, its source numeric value and unit, FDC source record and digest, archive SHA, profile revision, reviewer login, reason, timestamp, and `cookbook-launch-macros-v1` required nutrient set. It compares normalized profile kcal to the trusted source evidence and requires all four canonical macros. The immutable source fact rows must be populated by a **separately reviewed, SHA-verifying source importer**, not from reviewer RPC parameters. Merely presenting the stored archive SHA is not cryptographic proof of having parsed the official archive.

For the eight current source candidates, official-archive per-food digests and selected nutrient IDs are in `docs/evidence/ALL-225-USDA-EIGHT-PER-FOOD-ENERGY-DIGESTS-2026-11-12.json`. The digest algorithm is documented for exact reproducibility, and the source ZIP SHA is independently verified. Neither attestation nor complete macros implies source licensing, prep-state, alias, measurement or publication approval.

## Acceptance evidence and explicit blockers

The native isolated PostgreSQL test `scripts/test-v2-ingredient-native-concurrency.py` creates and destroys an ephemeral local database, two distinct credentialed reviewer sessions, ordinary athlete login, eight populated USDA-backed fixtures, immutable source evidence and negative fixtures. It confirms competing CAS, independent source-lock/update races, idempotent replay, expiry/revocation denials, explicit general-factor-only rejection, and eight source-bound attestations. It **refuses to run unless** `ALLIN_ISOLATED_NATIVE_POSTGRES=1` and PostgreSQL listens on `127.0.0.1`. It never uses any Supabase project. Complementary PGlite isolated role/RLS/source-stage tests are in the existing integration test scripts. Review evidence is filed under ALL-222 and ALL-225.

Remaining release gates: external IdP verified founder-designated operator and credential custody approval, source importer and public/private schema acceptance, published-review status-transition governance, two-person owner release authorization, deployment/rollback and retention policy, representative dedicated Supabase staging project, and installed-device acceptance. **Do not enable the calculation_ready writer path or create credentials/deploy in V2** until those gates are separately approved and tested.
