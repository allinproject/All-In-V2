# V2 Coach Action Capability Manifest — Ephemeral Authorization & Apply Contract

**Status:** Proposed implementation contract for ALL-222 / ALL-240 owner review; no database table or writer deployed  
**Owners:** ALL-240 capability/action lifecycle; each business domain retains its own canonical writer; ALL-217 Coach runtime  
**Repository:** allinproject/All-In-V2  
**Branch:** integration/v2-foundation  
**Reviewed:** 2026-11-10

## 1. Core decision: no persistent universal action store

The action-capability manifest is a **short-lived, per-turn authorization contract generated by the trusted app/Coach host**. It is not a canonical business object and does not need a database table.

The manifest exists to tell Coach what it may read, explain, navigate, preview or propose for the exact current context. It must not become:
- a generic AI-to-database writer;
- a second source of mutation authority;
- a duplicate idempotency ledger;
- a shadow store for goal, plan, food, recipe, gear, Recovery or Community state;
- durable authority that survives an account switch, target revision or manifest expiry.

The canonical domain remains the sole writer and persists the action in its existing domain-owned idempotency/version/audit mechanism. Where a domain currently lacks its writer, the capability is absent rather than implemented through a generic fallback.

## 2. Per-turn lifecycle

1. **Resolve trusted context.** Host determines authenticated account/session and retrieves exact canonical target identities, versions/revisions and current state from the relevant owner readers. Freeform screen text or old conversation summaries are not mutation authority.
2. **Build bounded manifest.** Host adds only the capabilities applicable to this turn and these exact target objects. It records a short expiry and a unique turn/manifest identity.
3. **Model proposes.** Coach may return only an action kind/action ID present in that manifest. The model cannot invent owner, target, revision, permissions, provenance or writer names.
4. **Preview.** For any material or destructive change, the host invokes the owner’s read/validate/preview capability. Preview returns the exact before/after diff, affected objects, warnings and expected version; it performs no canonical write.
5. **Explicit approval.** Athlete approves the exact preview/action. Approval is bound to the authenticated account, manifest ID, action ID, exact target identity/version and a one-time client action/idempotency key.
6. **Owner Apply.** Host dispatches to the typed domain-specific writer. The owner independently validates auth.uid, expected owner, target ownership, expected version/revision, allowlisted inputs and idempotency before mutation.
7. **Verify.** Owner returns the authoritative object identity/revision/version. Host re-reads the canonical object and verifies the exact target change. Coach reports success only after this owner-writer result is verified.
8. **Close transient capability.** The action is consumed, cancelled, expired or invalidated by a session/account/target change. A retry must use the owner’s exact idempotency contract, not replay a new write from freeform model text.

## 3. Ephemeral manifest shape

This is an in-memory typed contract, not a database schema. Exact implementation types are owned by ALL-240 and the Coach runtime.

~~~ts
type CoachCapabilityManifest = {
  manifestId: string;
  turnId: string;
  expiresAt: string;
  accountBinding: {
    userId: string;        // supplied by trusted host, never by the model
    sessionBinding: string; // opaque session/account generation binding
  };
  context: {
    kind: string;          // allowlisted typed context kind
    objectId: string;
    revisionOrVersion: string | number | null;
    ownerDomain: string;
  }[];
  actions: CoachCapability[];
};

type CoachCapability = {
  actionId: string;
  actionKind: string;      // finite registry owned by ALL-240
  ownerDomain: string;     // finite registered domain owner
  target: {
    objectKind: string;
    objectId: string;
    expectedVersion: string | number;
  };
  mode: "read" | "navigate" | "proposal" | "preview" | "apply";
  requiredInputs: string[]; // allowlisted typed input keys, not arbitrary SQL/patches
  confirmation: "none" | "explicit" | "destructive";
  expiresAt: string;
};
~~~

Security notes:
- The host supplies accountBinding and target versions after canonical reads. The model cannot set or override them.
- The runtime may add an integrity-protected opaque capability token; no client-visible value alone replaces owner-side authorization.
- Do not place service-role credentials, SQL, table names, unrestricted JSON patches or arbitrary RPC names in the manifest.
- A manifest must be small and task-relevant. Context-free chat receives no guessed mutation target or apply capability.
- Never trust a client-supplied provenance value such as host_action; the server/owner writer determines source and actor.

## 4. Preview / approval / Apply result contracts

### Proposal
A proposal is typed, non-persistent model output tied to one manifest action. It carries the exact proposed values and explanation but does not mutate canonical state.

### Preview
The owning domain validates the action against current canonical state and returns:
- exact target ID and current version/revision;
- proposed change and before/after diff;
- domain validation result and blocking/review warnings;
- expected owner and allowed action kind;
- whether explicit athlete approval is required;
- any downstream consequences the domain can deterministically identify.

Preview must not reserve a version, change a plan, or silently save a draft unless the owner explicitly defines a separate persistent draft workflow.

### Apply
Apply accepts a typed allowlisted payload, expected owner, expected target version, manifest/action identity and an idempotency key. It must not accept arbitrary model-generated database patches.

Owner writer result:
- outcome: applied, exact_retry, rejected_stale, rejected_permission, rejected_validation or other finite result;
- authoritative object ID;
- authoritative resulting version/revision;
- owner-domain event/reference;
- a concise outcome summary.

The host re-reads the object before displaying “saved”, “updated” or “applied”. A timeout/unknown result is reconciled by the same idempotency key and authoritative owner read; never send a new action with a new ID just because the response was lost.

### Cancel / decline
Declining a proposal leaves canonical state unchanged and is neutral. Cancel invalidates the exact preview/action. It does not create a shadow “declined change” in the business domain unless that domain has a product-approved reason to retain the decision. Coach may keep concise conversational context, but not durable business authority.

## 5. Where durable state belongs

| Durable fact | Owner / mechanism |
|---|---|
| Accepted goal and target revision | Goals (ALL-239) |
| Accepted Training plan revision and session identity | Training (ALL-246) |
| Completed activity and metric corrections | Completed Activity (ALL-243) |
| Food Log meal/entry action | Food Log (ALL-247) |
| Recipe save/configuration | Cookbook (ALL-218) |
| Pantry/Meal Plan/Meal Prep/prepared batch changes | Kitchen (ALL-248 / ALL-229) |
| Recovery plan/session | Recovery (ALL-238) |
| Canonical exercise identity and guided Strength result | Exercise Library / Completed Activity (ALL-258 / ALL-243) |
| User preferences, connection/consent and privacy lifecycle | Profile (ALL-251) |
| Social post/audience/race participation | Community/RaceHub (ALL-244) |
| Idempotency and mutation audit | Existing owner-domain private ledger/event record |
| Coach conversation and bounded result reference | Coach (ALL-217), referencing owner result only |

Do not create an allin_private global action ledger just to make every domain share one mutation system. Every owner already knows its own aggregate, version, idempotency, security and audit requirements. The manifest is a common orchestration envelope, not a second persistence owner.

## 6. Failure and invalidation rules

- Unknown action ID/action kind: refuse and offer a supported alternative; no fallback RPC.
- Manifest expired: rebuild from fresh canonical reads; do not silently renew old target authority.
- Account switch/sign-out/session generation change: invalidate every outstanding manifest, preview and pending Apply.
- Target object/revision changed: stale preview is invalid; reload, rebuild and re-present a new diff.
- Owner denies permission or target ownership: fail closed; do not retry as a more privileged domain.
- Required typed inputs missing: ask for the missing information or leave as proposal; never guess.
- User declines: canonical state remains byte-for-byte unchanged.
- Owner write timeout: reconcile exact idempotency key and object state before retrying; never tell the user it saved while outcome is unknown.
- Owner writer succeeds but readback is unavailable: report that Apply was accepted but verification is pending/unknown; do not claim verified completion.
- Unsupported/manual-only interactions (camera, barcode scan, device permission, ambiguous identity, destructive deletion) keep the direct UI flow and receive no artificial AI Apply capability.

## 7. Coach parity contract

For every supported action available in the manual UI, test whether Coach can reach the same canonical owner/writer with equivalent:
- authentication and authorization;
- target/version binding;
- validation and confirmation;
- retry/idempotency;
- cancel behavior;
- result/readback verification.

If a workflow is unsafe or inherently direct-manual (scan, permissions, unclear identity, sensitive deletion), document the exception rather than creating an AI-only shortcut.

Acceptance scenarios must include Food Log add/edit/move/delete; recipe configuration; Pantry/Shopping/Meal Plan/Meal Prep; Training plan revision; exercise substitution; Recovery; gear selection; privacy controls; stale version and account switch; rejected action; timeout reconciliation. All must prove the exact owner writer was used and no second business store was mutated.

## 8. Cross-domain invariants

1. One canonical owner/writer per business action.
2. Coach can read/explain/navigate/propose; explicit Apply invokes the actual owner.
3. Manifest availability is turn-scoped, context-scoped and target-version scoped.
4. The manifest cannot outlive or override the authenticated session.
5. Owner-side expected-user/version and idempotency checks remain mandatory even when the manifest is valid.
6. The UI and Coach share the same domain validations and writer contracts.
7. The model never reports a durable write until the owner result has been verified.
8. No generic persistent action store or generic SQL/mutation capability is introduced.

## 9. Owner decisions before implementation

1. Exact finite action-kind registry and owner-domain registry.
2. Which actions are read/navigation/proposal/preview/apply and their confirmation policy.
3. Manifest integrity token, lifetime and session/account invalidation mechanism.
4. Typed input schemas and canonical context freshness/refresh requirements.
5. Preview result contract and which changes require before/after consequences.
6. Timeout/reconciliation behavior for each owner writer.
7. What minimal owner result reference Coach may retain in conversation history without copying business data.
8. Coach parity test harness and acceptance coverage with ALL-230/ALL-241.

Until approved, do not create a generic Coach action database/table, grant Coach broad mutation RPC access, or let model output directly call an arbitrary domain writer.
