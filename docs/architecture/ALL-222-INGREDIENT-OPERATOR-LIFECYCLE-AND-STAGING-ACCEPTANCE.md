# ALL-222 / ALL-251 — Ingredient reviewer operator access and credential lifecycle

**Status:** Staged architecture and acceptance runbook only. No production operator, credential, API route, or published ingredient was provisioned or approved. This document implements the operator workflow for the **existing** canonical Ingredient Database and private writer; it is not a parallel authentication or nutrition system.

## Authority and principal model

The operator must be a specifically approved human linked to a trusted identity provider (IdP) issuer and immutable subject. The identity proof **must** come from a server-side validated IdP flow with enforced organization membership and MFA, not a user-controlled profile, `user_metadata`, a caller-supplied UUID, a JWT supplied by a mobile client, or a `service_role` key. An operator's approval authority must be issued by a separate authorized administrator with documented access review.

There are three distinct identities:

1. **Human identity:** verified `identity_issuer` + `identity_subject`, recorded with review evidence and approval reference. This is not an ALL IN athlete account or a private user-owned fitness profile.
2. **Dedicated PostgreSQL login:** one non-shared, revocable, non-inheriting `LOGIN` role per operator, authenticated by a secret from an approved vault over restricted TLS/database access. Credentials never enter Git, a mobile bundle, screenshots, CI logs, database review events, or `service_role` storage. No identity is considered created until a real IdP and approved vault are integrated and tested.
3. **Capability role:** the existing `allin_v2_ingredient_reviewer NOLOGIN NOINHERIT NOBYPASSRLS` role. The login must have an approved role grant with `INHERIT FALSE, SET TRUE` (PostgreSQL 17 semantics). Inside an isolated transaction the *authenticated* operator explicitly activates it with `SET LOCAL ROLE allin_v2_ingredient_reviewer`. PostgreSQL's `session_user` must remain the original dedicated human login; `current_user` becomes the restricted capability role. Calls directly from `authenticated`, `anon`, `service_role`, `postgres`, generic server pools, or an operator with no valid capability activation are rejected.

The only source of truth for the enrollment gate is `allin_private.v2_ingredient_review_operators` from `V2-INGREDIENT-OPERATOR-CREDENTIAL-LIFECYCLE-CANDIDATE.sql`. A trusted review process alone can set `enabled`, `identity_verified_at`, issuer/subject, credential vault *reference*, and expiry. The private functions reject disabled, revoked, expired or future-dated/unverified identities on every call and lock the enrollment row for the transaction. A fabricated registry row in a test does **not** prove the real IdP is connected.

## Provisioning and approval prerequisites

1. **Select and approve the real IdP, vault, access administrators, maximum credential/session lifetime, MFA and account recovery process in ALL-251/ALL-222.** Until then no real review login can be enrolled; do not silently nominate an ALL IN athlete as reviewer.
2. Have independent administrators verify the human subject from the provider's signed identity result; record approval/change reference and grant scope in private operational systems. Deny self-enrollment and self-approval; use least privilege and separate person from release approver.
3. Generate/rotate a **unique** database credential in the approved secret manager and provision a dedicated PostgreSQL LOGIN with minimum connection privileges; verify network/TLS policy and prohibit shared connection-pool reuse. Never embed actual password SQL in a migration or issue.
4. Once approved, grant ONLY the existing private reviewer capability to that login with explicit non-inheritance. Register the verified issuer, subject, vault reference, verification timestamp and expiry. Role membership alone cannot authorize a review; registry enablement alone cannot either.
5. Test `session_user`, `current_user`, limited EXECUTE, no direct table UPDATE, private audit denial and a controlled `candidate → needs_review → reviewed` transition. Run inside a real transaction, with an exact source SHA, idempotency UUID and expected profile revision. Audit the event and verify it atomically.
6. **Do not remove the `calculation_ready` hard stop** until ALL-222/ALL-225/ALL-228 have separately approved immutable source-energy/coverage evidence, authorization, publication and rollback; an energy attestation alone never authorizes publication.

## Rotation, expiry, offboarding and emergency revocation

- Set a finite expiry in the private registry. Rotate credentials through the approved vault and database credential lifecycle, with independently reviewed identity continuity and a new expiry; the immutable credential event audit records the change. Do not put secret material in the registry.
- Before disabling an operator, update the registry to `enabled=false`, set `revoked_at`, remove the capability role grant, disable the dedicated LOGIN and terminate that login's active database sessions. Credential/key revocation and session termination are **operations executed by the designated administrator**, not built-in effects of a SQL registry update; test their actual outcome before calling revocation complete.
- Existing reviewer functions acquire a share lock on the registry row so revocation coordinates with a transaction already under review. A successful pre-revocation commit remains auditable; calls following revocation must fail.
- Preserve immutable private review and credential audit events according to an approved retention/legal policy. Do not expose private audit or expired credential references through the mobile API, or silently delete rows to simulate offboarding.
- Emergency compromise: disable immediately, terminate sessions, revoke login and vault credential, review private audit and pending profile changes, quarantine unapproved sources, and follow a separately reviewed incident/recovery plan.
